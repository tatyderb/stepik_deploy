# SQL — задача с авторской или автоматической проверкой

Пример: [добавление пользователя](../examples/step_sql.md).
Автоматические проверки: [группировка и перевод между счетами](../examples/step_sql_test.md).
Перед загрузкой замените `lesson: 0` на ID своего урока.

После заголовка `## SQL Название` идёт условие в Markdown, затем секции
в произвольном порядке. Название секции — отдельная строка без отступа:

| Секция | Содержимое |
| --- | --- |
| `INIT` | SQL для создания таблиц и начальных данных |
| `SOLUTION` | Авторское SQL-решение |
| `CHECK` | Python-модуль с функцией `check(query, result)`; альтернатива `TEST` |
| `TEST` | Проверки результатов запросов и состояния базы; альтернатива `CHECK` |
| `CONFIG` | Необязательные настройки |

`INIT` и `SOLUTION` при отсутствии передаются пустыми строками. Их допустимость
для конкретной задачи проверяет Stepik. StepKIT не запускает авторское решение
и не вычисляет по нему ожидаемый ответ.

`CHECK` передаётся без изменения авторской логики и отступов. StepKIT проверяет
синтаксис Python и наличие функции `check`, но не выполняет этот код локально.
Stepik передаёт в функцию запрос ученика и результат выполнения; глобальный
`cursor` доступен для проверки состояния базы. Дополнительные функции и импорты
в модуле допустимы. Возможности среды исполнения определяются Stepik.

Код можно писать непосредственно под заголовком секции, как в примере,
либо оборачивать в блок из трёх обратных кавычек (`sql` или `python`).
Если код содержит отдельную строку `INIT`, `SOLUTION`, `CHECK`, `CONFIG` или
`TEST`, используйте обёртку. Удаляются только внешние переводы строк.
Экспорт использует такие блоки; вложенные тройные обратные кавычки в экспортируемом
коде пока не поддерживаются и вызывают ошибку вместо повреждённого Markdown.

## Пример шага SQL в Markdown

Ниже тот же шаг, что в файле примера. Его нужно поместить в Markdown-файл
урока с заголовком первого уровня и параметром `lesson`.

```markdown
## SQL Добавление пользователя

Добавьте в таблицу `users` пользователя с именем `Fluttershy`.
Существующие записи должны сохраниться.

INIT
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(20)
);

INSERT INTO users (name)
VALUES ('Rainbow Dash'), ('Twilight Sparkle');

SOLUTION
INSERT INTO users (name)
VALUES ('Fluttershy');

CHECK
def check(query, result):
    if "insert" not in query.lower():
        return False, "Use INSERT INTO statement to add a new row"
    count = cursor.execute("select * from users where id=3")
    if cursor.fetchone() == (3, "Fluttershy"):
        return True
    if count == 0:
        return False, "Cannot find a record with id=3"
    return False, "Inserted record is incorrect"

CONFIG
score: 1
allow_any_query: true
allow_multiple_queries: false
```

## Автоматическая проверка через TEST

Вместо Python можно описать проверки в секции `TEST`. Каждый блок содержит
цель проверки, строку `----`, ожидаемый JSON и завершающую строку `====`.
В одной секции можно перечислить несколько блоков; для зачёта должны пройти все.

Цель проверки:

- `RESULT` — результат единственного запроса ученика. Подходит для SELECT,
  включая JOIN, подзапросы, группировки и оконные функции.
- `RESULT 1`, `RESULT 2`, … — результат конкретного оператора ученика, нумерация с 1.
  При списке результатов простой `RESULT` выдаёт ошибку: номер нужно задать явно.
- SQL-запрос — выполняется через `cursor` после ответа ученика и проверяет
  состояние базы. Подходит для INSERT, UPDATE, DELETE и создания таблиц.

Например, вместо авторского `CHECK` в задаче про Fluttershy:

```text
TEST
SELECT id, name FROM users ORDER BY id;
----
[[1, "Rainbow Dash"], [2, "Twilight Sparkle"], [3, "Fluttershy"]]
====
```

Такая проверка подтверждает добавление записи и сохранность исходных строк.
Она не проверяет наличие слова `INSERT` в ответе.

### Расширенное сравнение

Вместо массива строк можно задать объект:

```text
TEST
RESULT
----
{
    "columns": ["name", "total"],
    "rows": [["Анна", 30.30], ["Борис", 40.00]],
    "ordered": false,
    "tolerance": 0.001
}
====
```

| Поле | Значение |
| --- | --- |
| `rows` | Ожидаемые строки; `[]` означает пустой результат |
| `columns` | Имена и порядок столбцов; проверяются только при явном указании |
| `affected_rows` | Число затронутых строк, например для UPDATE или DELETE |
| `ordered` | Учитывать порядок строк; по умолчанию `true` |
| `tolerance` | Абсолютная погрешность чисел; по умолчанию `0` |

Обязателен хотя бы один критерий: `rows`, `columns` или `affected_rows`.
Параметры `ordered` и `tolerance` применяются только к `rows` и задаются отдельно
для каждого блока. Порядок столбцов всегда значим. При `ordered: false`
дубликаты сохраняются: две одинаковые строки нельзя заменить одной.
Сравнение без порядка требует сопоставления строк, поэтому для больших таблиц
предпочтительнее `ORDER BY` и упорядоченное сравнение.

`null` соответствует SQL NULL; пустая строка и текст `"NULL"` ему не равны.
Числа, включая полученный от драйвера `Decimal`, сравниваются по значению;
строка `"1"` не равна числу `1`. Даты задаются строками `YYYY-MM-DD`,
дата и время — `YYYY-MM-DD HH:MM:SS`, при необходимости с дробной частью секунд.
JSON boolean сравнивается строго; для MySQL BOOL/TINYINT обычно нужны числа 0 и 1.
Двоичные значения и специальные типы лучше привести в проверочном SQL к тексту
или числу. Для иной логики используйте ручной `CHECK`.

### Несколько проверок

```text
TEST
RESULT 1
----
{"affected_rows": 1}
====
RESULT 2
----
{"affected_rows": 1}
====
SELECT id, balance FROM accounts ORDER BY id;
----
[[1, 75], [2, 225], [3, 300]]
====
SELECT SUM(balance) FROM accounts;
----
[[600]]
====

CONFIG
allow_multiple_queries: true
```

Полный пример с `INIT` и `SOLUTION` — в [step_sql_test.md](../examples/step_sql_test.md).
Число затронутых строк отражает значение, возвращённое Stepik/драйвером;
для гарантии нужного состояния данных дополнительно проверяйте таблицу.

### Порядок выполнения и ограничения

Согласно [документации Stepik](https://stepik.org/lesson/635539/step/1?unit=634546),
платформа использует MySQL 8.0.21 и перед каждой посылкой создаёт новую базу:
`INIT` → ответ ученика → `check(query, result)`. При нескольких операторах
`result` является списком словарей с `rows`, `columns`, `affected_rows`.

Все блоки `TEST` проверяют **одну базу после одного запуска ответа**. Они не
создают независимые наборы исходных данных и не запускают решение повторно.
Проверочные SQL-запросы выполняются последовательно; рекомендуются запросы
только на чтение, поскольку изменения повлияют на следующие проверки.
`SOLUTION` не выполняется генератором и не превращается в ожидаемый ответ.

Сгенерированный модуль возвращает `True` только при успехе всех блоков.
При несовпадении возвращается `False` и сообщение на русском с номером проверки,
без раскрытия ожидаемых данных. Ошибка выполнения проверочного SQL также
означает незачёт; перед публикацией нужно проверить запросы автора.

При экспорте неизменённый сгенерированный модуль восстанавливается в `TEST`.
Если код изменён вручную или создан другой версией генератора, сохраняется
полный `CHECK`. Код при экспорте не исполняется.

Генератор проверен локально на формате результатов из документации и SQLite
с адаптером курсора. Эти тесты не заменяют проверку MySQL и исполнения на Stepik.

## Настройки

| Опция | По умолчанию | Значение |
| --- | --- | --- |
| `score` | `1` | Целое неотрицательное число баллов |
| `allow_any_query` | `true` | Разрешение пробного запуска кода (`is_run_user_code_allowed`), не ограничение SQL-команд |
| `allow_multiple_queries` | `false` | Несколько SQL-операторов в ответе ученика (`is_multiple_statements_allowed`) |

Разделители опций — `:` или `=`. Неизвестные и повторные опции, повторные
секции и невалидные значения вызывают ошибку.
Укажите ровно одну непустую секцию: `CHECK` или `TEST`.

### Специфичные поля шага SQL

`block.name` равен `sql`. Поля `block.source`:

- `init_sql` ← `INIT`;
- `solve_sql` ← `SOLUTION`;
- `check_code` ← `CHECK` или модуль, сгенерированный из `TEST`;
- `is_run_user_code_allowed` ← `allow_any_query`;
- `is_multiple_statements_allowed` ← `allow_multiple_queries`.

Баллы передаются в `stepSource.cost`. Поля и значения флагов по умолчанию
сверены с публичным компонентом `stepic/components/step-editor/quiz-editor/sql`
в [коде редактора Stepik](https://cdn.stepik.net/static/frontend-build/stepic.js).
Это не заменяет проверку создания и исполнения задачи на сервере.

В примере сохранён исходный авторский CHECK: он проверяет наличие `insert`
в тексте ответа и запись с ID 3. Он не проверяет сохранность остальных записей
и не является полноценным анализатором SQL. Дополнительные требования нужно
явно проверять в авторской функции.
